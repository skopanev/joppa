Read joppa_tree for the workspace types, parents, references, questions, status rules and typed fields. Use those rules for the current workspace.
A typed field (fields.<name>) has type, values and from. The order of values is the rollup priority: the first value wins. from own: the node stores the value. from children, links or parent: the server computes and stores it, a read gives it in data, and a save that sends it is refused.
A list field or a multiple reference with from children gives the sorted union of the values of the children, each value once.
Use joppa_objects to find and read current objects. Read one historical revision only when needed. Use joppa_search to find related work.
Read joppa_help with op for the operation you need.
Resolve a copied public ID with joppa_search({"workspace":"...","query":"<ID>"}): the reply gives only that object, with exact_id. Never guess local IDs.

Read an object before you change it. Send its current revision. On an update, send only the data fields that change: data merges by key, and null removes a field. Omit parent and links to keep them. Send clean: true to replace data whole.
Create with save_object and revision:0. Omit id so the server generates it. Preserve the existing id when editing.
Write a title and body that answer the question of the type.
A write takes a public item ID where it takes an address of the workspace. The journal stores the address.
Use joppa_batch for related writes. Retry identical input with the same request_id after a lost response.
Set data.workspace on a node to bind a child workspace; use set_remote_links for links across workspaces.

Save a raw incoming signal as an Inbox item: the type with inbox: true, parent:null. Preserve its original text and language.
After analysis, put the lasting content into a Source and into REQ and AC nodes, and link them. Then archive the Inbox item with archive_object.
A Source records an owner decision, a specification or an external standard at a fixed version. When the schema defines ac.sources, set data.sources on every AC. Do not copy sources to the REQ.
Keep comments (op note) for discussion. A comment is not an Inbox item and not a Source.
Use a short title. Put context, conditions and evidence in body. Use clean Markdown in authored text.
Show object references as [Title](kind:id), using the title and address you read. Markdown links do not replace structural links.

Read open work with joppa_history open=true. Mark each processed entry with joppa_history_mark.
Before implementation, score each REQ and AC with the 11111 checklist: Grounded, Atomic, Unambiguous, Minimal, Verifiable. Implement only a node that scores 11111. Read joppa_help section objects for the rules.
Gate 6 is Reuse (R): search the codebase and the Tech root for shared types, packages, libraries, helpers, modules and contracts. Use the code graph index (codebase-memory, CBM: search_graph, search_code, SIMILAR_TO) when it is connected. Reuse what exists. Do not write duplicates.
The agent that writes a node never scores it. An independent Reviewer agent with another alias scores 11111 + R before any test of the AC exists. On a HOLD, the Writer agent asks the owner one closed question in the chat, updates the Source and the AC, and the Reviewer scores again.
After APPROVE, one agent writes the code for the AC with its Tasks (one AC can have 1..N Tasks). Another independent agent writes the acceptance Test nodes of the same AC as a black box, from the AC and its Sources, so the coder cannot fit the code to known tests.
There is no manual acceptance. Record the owner decision as a Source. Green Test nodes prove the criteria.
Create a Task only under an AC, directly before you implement that AC. Never create Tasks in advance while the tree changes.
Check existing Tasks before creating work. Set blocking dependencies explicitly. Read current dependency evidence before changing a revision pin.
A Task is a node like any other: data.assignee names the person or the agent alias, such as lane3, a typed field such as data.stage gives its state, and archive_object ends it. Put the Git commit of finished work in data.commit. Test results prove a criterion. A finished Task does not prove a criterion.
No criterion, no test. A test is a node: save_object with kind test under its AC. Every test in the repository must have a present test node.
Write the title as the scenario in business language, with concrete numbers and no code. Put the inputs and the expected outcome in body. Set case: nominal (the normal working path), boundary (the edges of limits) or off_nominal (errors and safe refusals). Set command: the exact isolated command that runs this one test. A manual check is no test node: attach its evidence file to the AC with check_result.
Check each test node with Test-5: (1) business language and concrete numbers, no code. (2) One test, one diagnosis. (3) The normal path, the boundaries and a safe failure. (4) The real system, no mocks of the logic under test. (5) A fast, isolated command.
All tests under one AC together cover 100% of its conditions. The AC is green only when all of them are green at the same time.
Never add or rename a test without its test node in the same change. Archive the test node of a deleted test, and the test nodes of a criterion before the criterion.
In joppa_record_results, name each test by test:<id> or by its public item ID: it binds that one test node. A title binds every present test node with that title, also as an earlier title of a renamed node.
joppa_record_results gives "unbound": the tests of the record that have no present test node. The server keeps their results under the given name, so a test node with that title counts them later. A full-run record must give "unbound": [] before a merge.
Use the configured test_results rules. Preserve failures and evidence. Record human decisions only with explicit human instruction.

Prefer English for new technical text. Preserve existing text and quotations in their original language. Apply the writing rules below.

An HTTP 503 answer with Retry-After: 30 and JSON-RPC error -32000 means maintenance, such as a deploy. Wait 30 seconds and retry the same call with the same request_id.
