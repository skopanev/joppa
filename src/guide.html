The product tree and its tasks

Suggested default tree: Domain → Capability → REQ → AC. Each workspace schema sets its own levels and the question each level answers.

  1. Domain

    Question it answers
    Which part of the business is this?
    Example
    Subscriptions and access.

    1. Capability

      Question it answers
      What can the product do?
      Example
      Restore paid access.

      1. REQ Requirement

        Question it answers
        What must the product guarantee?
        Example
        A customer with an active subscription keeps paid access after signing in again.

        1. AC Acceptance criterion

          Question it answers
          What must be true to accept this requirement?
          Example
          On iOS, a customer with an active subscription has access to paid features after signing in again.

          1. Task Work linked to an object

            Question it answers
            What work needs to be done?
            Example
            Implement paid-access restoration after sign-in in the iOS app.

            The workspace schema selects permitted task parents. Each task has one parent. The default tree places tasks under acceptance criteria. One criterion can have several tasks. Other schemas can use different parent types.

We suggest opening an object to read its linked work. The workspace schema selects the permitted task parents.

The workspace schema defines the tree. We suggest domains and capabilities as default levels for organizing commitments. Each type has a status rule: tests, children, links or none. Owner acceptance is tracked separately.

Status circles show the current status. A criterion is green when every test in its list passes in its latest record. It is red when one test fails. It is grey when it has no test list, or when a listed test has no record after the change. A group or a requirement takes its status from its children. A node with the links rule takes its status from the objects that link to it. Pending decisions or work produce yellow. An empty branch cannot be green. Task completion does not make a criterion green.

What a test report proves

A criterion lists the tests that prove it, by file and name. A member records the test results of each commit with joppa_record_results. Only these records decide the status. A completed Task alone proves nothing.

Each listed test needs a recorded result. A failed test makes the criterion red. A test without a result keeps it grey. One criterion can list several tests. One test can prove several criteria.

RecordThe test results of one commit, which a member records with joppa_record_results.

Read green as “the listed tests pass on this commit”. The criterion shows the commit of each test result. Compare that commit with the deployed release before you treat a green card as evidence about production. A failed test keeps its failure message in the history of the criterion.

A suggested path from a requirement to a release

We suggest the following workflow. The agreed scope is iOS. Android and web require their own scope decision.

  1. Agree on the behavior

    REQ: A customer with an active subscription keeps paid access after signing in again. AC: On iOS, paid features are available after sign-in for that customer.

    The owner confirms the requirement. The agent assesses the criterion and marks it ready. Two Tasks deliver it: the backend returns the subscription entitlement, and the iOS app refreshes access after sign-in.

  2. List the tests, then run them

    The agent saves the test list of the criterion. Both Tasks can be complete while the criterion is still grey: it waits for the recorded results.

  3. Keep the failure and fix the cause

    Failed The backend reports an active subscription, but the app shows the purchase screen. The failed result stays in history.

    The agent fixes the app. The agent runs every test again and records the results.

  4. Verify, then ask the owner to accept

    Passed Every listed test passes in its latest record. The requirement is ready for acceptance. Agent confidence, Task completion and silence cannot take the place of this decision.

  5. Check the next release on its own commit

    A later commit changes the backend. The agent runs the same tests again and records the results. A test that fails makes the criterion red again.

    Before launch, compare the release commit with the commit of the test results. The joppa. status shows only what the reports prove.

Changed wording needs fresh evidence

A change to the wording of a criterion makes it grey again. The next records decide its status. Earlier results stay in history.

The agent compares the implementation and the tests with the new wording. It updates them where necessary. Suitable test code can stay. Old results do not count for the new wording.

Comments do not create revisions or block work. An agent must not silently expand an iOS condition to Android or web. People decide changes to scope and policy.

When work needs another pass

What happens next, and who moves it forward
SituationNext action
A test failsThe agent finds the cause and fixes it. The next record shows the new result. An older pass cannot hide a newer failure.
A listed test has no resultThe criterion stays grey. The agent runs the test and records the result, or corrects the test list.
The deployed commit differsThe agent runs the tests on that commit and records the results. Old results stay in history and are not proof about the new commit.
The owner finds a defectThe owner records the reason. The agent adds a test that fails on the defect, then fixes it. Changed expected behavior needs new wording.
Requirements or policy conflictThe agent records the specific question and the person who decides. The affected criterion waits. Independent ready criteria can continue.

History keeps wording, reports and decisions with their authors and times. Acceptance records what the owner considered sufficient. It does not prove that every possible condition is known.
