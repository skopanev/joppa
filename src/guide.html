How it works

This is a suggested method. A tree connects product commitments, work and evidence. Choose the levels and questions that fit your workspace.

Owner decided

The owner gives a decision in the chat. The agent records it as a Source.

Work done

A Task records what was changed.

Tests passed

Every test of a criterion passes in its latest record.

One workspace per product

A product that spans several repositories keeps one shared tree. Link work to the affected repositories.

Switching workspace changes the entire tree, requirements and discussions.

Workspaces can depend on each other. A node can stand for another workspace and show its status. An object can link to an object in another workspace. Each person sees only the workspaces that they can read.

A blocking remote link keeps the revision of its target. Work waits until the target, and everything that the target depends on, is green. A changed or archived target asks for a review. Work waits until a person pins the new revision or removes the link.

The product tree and its tasks

Suggested default tree: Domain → Capability → REQ → AC → Test, and Tech → REQ → AC → Test. Each workspace schema sets its own levels and the question each level answers.

  1. Domain

    Question it answers
    Which part of the business is this?
    Example
    Subscriptions and access.

    1. Capability

      Question it answers
      What can the product do?
      Example
      Restore paid access.

      1. REQ Requirement

        Question it answers
        What must the product guarantee?
        Example
        A customer with an active subscription keeps paid access after signing in again.

        1. AC Acceptance criterion

          Question it answers
          What observable condition makes this requirement acceptable? Use (1) Given / When / Then for a state transition or action, or (2) a direct rule for an invariant, limit or disclosure.
          Example
          On iOS, a customer with an active subscription has access to paid features after signing in again.

          Each AC names its Sources. The REQ gets no copy of them.

          1. Test Proof of the criterion

            Question it answers
            Which scenario proves this criterion?
            Example
            A customer with a 12-month subscription signs in again on iOS and opens all 3 paid features.

            The title states the scenario in business language, with concrete numbers and no code.

          2. Task Created on demand

            Question it answers
            What work implements this criterion?
            Example
            Implement paid-access restoration after sign-in in the iOS app.

            Create a Task under the AC directly before you implement it. Do not create Tasks while the tree is filled or agreed: the tree changes too fast.

  2. Tech Shared technical contracts

    Question it answers
    Which shared technical area does this root own?
    Example roots
    API, Database, Integrations, Platform, Security, Infra.

    1. REQ Requirement

      Question it answers
      Which technical contract must the product obey?
      Example
      The session endpoint reports paid access.

      1. AC Acceptance criterion

        Question it answers
        Which exact contract makes this requirement acceptable?
        Example
        POST /auth/session returns HTTP 200 with paid_access: true when the subscription row is active.

        Test nodes and Tasks attach here, as under a product AC. Link work across areas with depends_on.

  3. Inbox RAW

    Question it answers
    What did the source report, and who sent it?
    Example
    A customer writes that paid features are locked after a new sign-in.

  4. Source SRC

    Question it answers
    Which owner decision, specification or external standard grounds these rules, and at which version?
    Example
    Owner decision, version 1: paid access survives a new sign-in on iOS.

Open an object to read its linked work. The workspace schema selects the permitted task parents.

The workspace schema defines the tree. One vertical applies everywhere: REQ → AC → Test, and a Task under the AC. Each type has a status rule: own, children, links or none. There is no manual acceptance: green Test nodes prove the criteria.

Nodes connect by relations. The tree schema keeps the registry of relations: each key has a title and a description. Every workspace has depends_on and related. depends_on makes a node wait until its target is green and refuses cycles. related is a reference that blocks nothing. A member can add a flow, such as the screens of a client journey: a flow allows cycles, blocks nothing and resets no test. A node holds an edge list under each key, and an edge can name a condition in when. A member changes the registry with set_tree_schema and put_relations, and reads the edges of a node in pages of 25 with relations_of. in_relation reads the nodes of one relation, and Flow view of the board draws them from left to right. A link to an object of another workspace uses set_remote_links.

Status circles show the current status. Each test is a node under its criterion. A test node is green when the latest record of its test passes, red when it fails, and blue when it has no record after the change. A criterion, a group or a requirement takes the highest tone of its children: red, orange, yellow, blue, green. A criterion without a test node is orange. A node that waits for a dependency is yellow. A node with the links rule takes its status from the objects that link to it. The workspace schema sets the list of status tones and their colours. An empty branch cannot be green. Task completion does not make a criterion green.

Inbox, sources and comments

Keep three items apart:

  1. Inbox item (RAW). A raw incoming signal before analysis. It keeps the original text and language.
  2. Source (SRC). An owner decision, a specification or an external standard with a fixed version. Every AC names at least one Source.
  3. Comment. A discussion inside a card. It adds no revision and grounds no rule.

After analysis, the agent puts the lasting content into a Source and into REQ and AC nodes. The agent gives them related edges, then archives the Inbox item.

Before implementation

The Reviewer agent reads the full node, its parent and the verbatim text of every linked Source. It also reads the existing mechanisms in the codebase and the Tech root. Then it scores each REQ and AC with the 11111 checklist and gate 6, Reuse:

  1. G, Grounded. Every condition, value, limit and branch appears in the Source text. Code and tests alone are not a Source. On 0: strip the text, or ask for the Source.
  2. A, Atomic. One rule, or one cohesive schema. On 0: split the node.
  3. U, Unambiguous. One reading and one implementation path. On 0: ask one closed question with concrete options.
  4. M, Minimal. The node specifies the software, not manual duties, and adds nothing that an existing mechanism covers. On 0: strip, or ask.
  5. V, Verifiable. A finite deterministic automated test proves Pass or Fail. On 0: rewrite and name the missing trigger or outcome.
  6. R, Reuse. The node and its plan use the ready shared types, packages, libraries, helpers, modules and Tech contracts of the codebase. Search with the code graph index (codebase-memory, CBM) where it is connected. On 0: reuse what exists, or ask the owner to choose.

Only a node that scores 11111 and R goes to implementation. The score is tied to the revisions of the node, its Sources and its dependencies.

Independent agents, one loop. The agent that writes a node never scores it. This is a process rule for agents.

  1. Writer. The Writer agent talks with the owner in the chat. It records each decision as a Source and writes the REQ and the AC.
  2. Reviewer. An independent Reviewer agent with another alias checks 11111 and R. No test of the AC exists yet.
  3. HOLD. A gap in the Source, a fork or a conflict with an existing mechanism gives a HOLD. The Writer does not invent an answer. It asks the owner one closed question in the chat and updates the Source and the AC. The Reviewer checks 11111 and R again.
  4. Pass. Two independent agents start on the AC. One agent writes the code with its Tasks: one AC can have one Task or more. The other agent writes the acceptance Test nodes as a black box, from the AC and its Sources, so the coder cannot fit the code to known tests. The work ends when all Test nodes of the AC are green at the same time.

What test results prove

Each test that proves a criterion is a test node under it. A member records the test results of each commit with joppa_record_results and names each test by test:<id>, which binds that one test node. A title binds every present test node with that title. Only these records decide the status. A completed Task alone proves nothing.

Each test node needs a recorded result. A failed test makes the criterion red. A test without a result keeps it blue. One criterion can have several test nodes. A test that proves several criteria has one node under each.

Write a test that proves a criterion
PartExample
CriterionOn iOS, a customer with an active subscription has access to paid features after signing in again.
TitleA customer with a 12-month subscription signs in again on iOS and opens all 3 paid features.
BodyInputs: an active 12-month subscription. The customer signs out, then signs in. Expected: the 3 paid features open, and the purchase screen does not appear.
Casenominal: the normal working path. boundary checks the edges of limits, and off_nominal checks errors and safe refusals.
CommandThe exact isolated command that runs this one test. Only a test that a person does by hand has none: it attaches its evidence with joppa_attach.
RecordThe test results of one commit, which a member records with joppa_record_results.

Check each test node with the Test-5 checklist:

  1. Business language and concrete numbers. No code.
  2. One test, one diagnosis.
  3. The normal path, the boundaries and a safe failure.
  4. The real system. No mocks of the logic under test.
  5. A fast, isolated command.

All tests under one AC together cover 100% of its conditions. The AC is green only when all of them are green at the same time.

Read green as “every Test node of the criterion passes on this commit”. The criterion shows the commit of each test result. Compare that commit with the deployed release before you treat a green card as evidence about production. A failed test keeps its failure message in the history of the criterion.

A suggested path from a requirement to a release

The example below follows one requirement. The agreed scope is iOS. Android and web require their own scope decision.

  1. Agree on the behavior

    REQ: A customer with an active subscription keeps paid access after signing in again. AC: On iOS, paid features are available after sign-in for that customer.

    The owner decision is a Source, and the criterion names it. The Reviewer agent scores the criterion 11111 and R before any test exists, and finds reusable code. Then the coding agent creates two Tasks: the backend returns the subscription entitlement, and the iOS app refreshes access after sign-in.

  2. Write the Test nodes, then run them

    Another independent agent writes the acceptance Test nodes of the criterion as a black box: the normal path, the boundaries and a safe failure. Both Tasks can be complete while the criterion is still blue: it waits for the recorded results.

  3. Keep the failure and fix the cause

    Failed The backend reports an active subscription, but the app shows the purchase screen. The failed result stays in history.

    The agent fixes the app. The agent runs every test again and records the results.

  4. Verify with green Test nodes

    Passed Every Test node of the criterion passes in its latest record. The criterion is green. Agent confidence, Task completion and silence cannot take the place of the recorded results.

  5. Check the next release on its own commit

    A later commit changes the backend. The agent runs the same tests again and records the results. A test that fails makes the criterion red again.

    Before a release, compare the release commit with the commit of the test results. The joppa. status shows only what the reports prove.

Changed wording needs fresh evidence

A change to the wording of a criterion makes it blue again. The next records decide its status. Earlier results stay in history.

The agent compares the implementation and the tests with the new wording. It updates them where necessary. Suitable test code can stay. Old results do not count for the new wording.

Comments do not create revisions or block work. An agent must not silently expand an iOS condition to Android or web. People decide changes to scope and policy.

When work needs another pass

What happens next, and who moves it forward
SituationNext action
A test failsThe agent finds the cause and fixes it. The next record shows the new result. An older pass cannot hide a newer failure.
A Test node has no resultThe criterion stays blue. The agent runs the test and records the result, or archives a Test node that no test proves.
The deployed commit differsThe agent runs the tests on that commit and records the results. Old results stay in history and are not proof about the new commit.
The owner finds a defectThe owner records the reason. The agent adds a test that fails on the defect, then fixes it. Changed expected behavior needs new wording.
Requirements or policy conflictThe agent records the specific question and the person who decides. The affected criterion waits. Independent criteria can continue.

History keeps wording, reports and decisions with their authors and times. Green tests do not prove that every possible condition is known.
